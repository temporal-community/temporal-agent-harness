# SDK-Neutral Sandboxes

**Status:** ✅ Implemented (see `tests/harness/test_sandbox.py`).
**Scope:** `harness/sandbox/` (new package), `harness/agent_workflow.py` (`LazyInjection` +
`injection_slots` + resolution in `run_tool`), `harness/agent.py` (re-export).

## 1. Why

The harness's headline is "bring your own AI SDK," with integrations for Gemini, OpenAI Agents,
Pydantic AI, and more planned. But isolated execution — the thing an agent needs when it must run
model-authored code or browse data it should not hold in process — was reachable only from the
OpenAI Agents SDK, in `ai_sdks/openai_agents/sandbox/`.

That coupling ran three layers deep:

1. **Types.** The sandbox modules import `Manifest`, `SandboxSessionState`, `BaseSandboxClient`, and
   friends from `agents.sandbox`, so using the seam means depending on `openai-agents` for type
   definitions even when the agent loop is something else.
2. **Registration.** Activities are generated by `OpenAIAgentsPlugin(sandbox_clients=[...])` — they
   exist only if that plugin is installed on the worker.
3. **Delivery.** The session reaches a tool through
   `RunConfig(sandbox=SandboxRunConfig(client=temporal_sandbox_client(name)))`, and it is the OpenAI
   *runner* that creates the session and makes it reachable. An agent on any other SDK has no
   `RunConfig`, so a tool body ends up with no sandbox object in scope.

Layers 1 and 2 are inconvenient. Layer 3 is the real gap: `TemporalSandboxClient` is standalone
activity dispatch, so an author *can* hand-wire create/resume themselves — but every adopter doing
that separately, differently, is the outcome worth avoiding.

This feature adds a harness-owned sandbox seam that any SDK integration can use, and leaves the
existing OpenAI-specific one untouched.

## 2. Shape

Three pieces, in the order an author meets them.

### 2a. `harness/sandbox/protocol.py` — the contract

`SandboxBackend` is a `Protocol` an integrator implements for their sandbox provider: create,
resume, delete, exec, run_code, read, write, ls, running. Nothing in the module imports an AI SDK,
so **one backend implementation serves every SDK the harness wraps.**

`SandboxState` is the serializable identity — the only sandbox data that enters workflow history.
Its `backend_ref` is opaque to the harness on purpose: a backend whose claim is idempotent on
caller-supplied identity (one sandbox per tenant, per conversation, per repository) can put that
identity in it and get replay-safety *structurally* — any retry, on any worker, re-derives the same
sandbox with no id to thread. Backends without that property use `create`/`resume` as before.

Two error types carry meaning the harness acts on:

- `SandboxUnavailable` — quota, rate limit, capacity. Retryable, so with a retry policy this is
  already a queue. When sandboxes are genuinely scarce, route sandbox activities to their own task
  queue and size worker concurrency to capacity; backoff then becomes bounded admission control.
- `SandboxReclaimed` — **the sandbox is gone and anything written into it is lost.** Non-retryable,
  because a blind retry hands the agent a fresh empty workspace with no signal. This distinction is
  the one adopters most often discover late: durable execution gives you a durable *log*, not a
  durable *filesystem*.

`SupportsHydration` is an optional capability for backends that can read the data store themselves.
The payload crossing the activity boundary is then a *locator* rather than the data. That matters
for two independent reasons: size (workspace contents never become a payload, so no large-payload
codec is involved) and copies (by-value transfer creates an additional persisted copy in whatever
store the codec offloads to, with its own retention and replay coupling).

### 2b. `harness/sandbox/provider.py` — worker side

`SandboxProvider(name, backend)` emits the backend's activities, each prefixed with the provider
name, so several backends coexist on one task queue and the workflow side selects between them by
name alone. It keeps a small cache of resumed states and calls `backend.resume` on a miss — which is
what lets a sandbox survive losing the worker that created it. Backend errors are translated:
retryable ones propagate so Temporal backs off, terminal ones become non-retryable
`ApplicationError`s.

### 2c. `harness/sandbox/handle.py` + `injection.py` — workflow side and delivery

`SandboxHandle` holds a provider name plus a `SandboxState`, and every method is one activity. It is
safe to hold for a whole run and safe across replay because it holds no live connection.

**Sandbox tools are inline tools.** A handle dispatches its own activities, so it works anywhere
`workflow.execute_activity` is legal — a `@agent.tool_defn` body qualifies, an
`@agent.activity_tool_defn` body does not. The durability comes from each sandbox *operation* being
an activity, not from wrapping the tool in one. The handle raises a clear error if used outside a
workflow rather than failing obscurely.

Delivery is the part that did not exist. It builds on the harness's own `Injected[...]`, which is
already the mechanism for "the workflow supplies this parameter, not the model" — with one gap: an
SDK adapter builds its toolset **once**, at module level, so anything in that static `injections`
mapping is also static. A sandbox belongs to a single run.

`LazyInjection` (in `agent_workflow.py`) closes that gap generically: an injected value may instead
be an object with `async def resolve_injection(runner)`, which `run_tool` awaits at dispatch. So the
*declaration* is static and the *resolution* is per-run. `SandboxRef("workspace")` is the canonical
implementation; `attach_sandbox(runner, "workspace", options)` supplies the per-run part, and the
sandbox is claimed lazily on first use — a run whose model never calls a sandbox tool never pays for
one.

`run_tool` gained four lines and no sandbox knowledge: it resolves anything implementing
`LazyInjection` and is otherwise unchanged. Plain injections still pass through by identity, so the
common path costs one `isinstance` per entry.

## 3. Usage

```python
# worker
provider = SandboxProvider("workspace", MyBackend())
Worker(client, task_queue="agents", activities=[*provider.activities(), ...])

# tool — declared once, at module level
@agent.tool_defn()
async def grep_workspace(sandbox: Injected[SandboxHandle], pattern: str) -> str:
    """Search the workspace for `pattern`."""
    result = await sandbox.exec("grep", "-rn", pattern, ".")
    return result.stdout or f"no matches for {pattern!r}"

INJECTIONS = {"sandbox": SandboxRef("workspace")}

# workflow — per run
attach_sandbox(self._runner, "workspace", MyOptions(tenant_id=config.tenant_id))
```

Because resolution happens in `run_tool`, which every SDK integration already goes through, there is
no per-SDK sandbox code anywhere — and a Code Mode host function is just a harness tool, so
model-authored scripts can call sandbox tools with no extra plumbing.

## 4. Settled decisions

- **No `acquire(scope, identity)` on the protocol.** It was considered and rejected: most backends
  (Docker, a local subprocess, hosted sandbox APIs) create-and-return-an-id, so an idempotent-claim
  method would serve few of them. Backends that *do* have idempotent claim express it inside
  `create` and store their identity in `backend_ref`, which is strictly less surface for the same
  benefit.
- **Options cross as a plain mapping.** `CreateArgs.options` is a `dict`, and the provider validates
  it into the backend's declared `options_model` worker-side. That avoids pydantic discriminator
  plumbing for what is a backend-private type.
- **Hydration is optional, not core.** A backend that cannot reach a data store is unaffected;
  calling hydrate on one fails as a terminal error naming the capability it lacks.
- **`LazyInjection` is generic, not sandbox-specific.** Keeping it in the core meant `run_tool` needs
  no sandbox import, and any other per-run dependency (a lease, a connection, a tenant-scoped
  client) gets the same treatment for free.
- **Bytes travel base64 under a JSON payload converter** (`JsonSafeBytes`), matching the approach in
  the existing OpenAI sandbox models, so `read`/`write` are binary-safe.

## 5. Not in scope

- **The existing OpenAI Agents sandbox integration is untouched.** It could be re-expressed as an
  adapter over this protocol later; that is a separate change with its own compatibility surface.
- **No admission control.** Sandbox scarcity is handled by activity retry plus, if an adopter wants
  bounded queuing, a dedicated task queue or a lease workflow. Resource admission sits below an
  agent framework, and the capacity is known by the sandbox service, not by the harness.
- **No bundled backend.** `tests/harness/test_sandbox.py` has an in-memory one that doubles as the
  reference implementation. A runnable example against a real sandbox provider is a natural
  follow-up.
